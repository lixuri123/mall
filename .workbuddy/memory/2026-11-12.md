## B 阶段「超时订单取消的消息可靠性」落地（按用户给的长方案，指定使用 mall-local 容器）

- **关键坑（务必记住）**：容器 MySQL 默认 UTC，而 `application-dev.yml` JDBC 是 `serverTimezone=Asia/Shanghai`，DB `NOW()` 与应用写入的 `create_time`/`expire_time` 差 8 小时，导致 A 回归 `OrderTimeOutScanTest`、`PortalOrderDaoAtomicSqlTest` 失败。修复：`docker-compose-local.yml` 加 `command: --default-time-zone=+08:00` 与 `TZ: Asia/Shanghai`，重建 mysql 容器；`document/docker/LOCAL.md` 说明。
- **核心实现**：`oms_order.expire_time` 下单时按当时配置固化，系统取消只认它（NULL 则 REJECTED + 告警，不猜测）；下单同一事务写订单/锁库存/券积分/`expire_time`/`PENDING` 消息，删除全部 afterCommit / 事务内直发 MQ；`oms_order_message` + `oms_order_consume_failure` + `oms_order_expire_backfill_exception` 三表；`OmsOrderMessageDispatcher` 用租约 + `attempt_version` CAS 领取（短事务提交后才做网络发布），Publisher Confirm(correlated) + mandatory Return 区分 CONFIRMED/NACK/UNROUTABLE/UNKNOWN/ERROR，`SENT` 只代表发布成功；`CancelOrderReceiver` 手动 ACK（业务事务提交后才 ack）、固定 TTL 重试队列（统一延迟，避免每消息 TTL 队头阻塞）、毒消息与超次进 DLQ 并落失败记录、提前投递 JOIN `oms_order` 重排到固定 `expire_time`；双层兜底 = 消息表扫描 + 订单表按 `expire_time`/id 游标扫描；`OmsOrderMessageMetricsLogger` 9 项指标与 ERROR 告警；运维接口 `OmsOrderMessageAdminController` 默认不注册。
- **SQL / 拓扑**：`document/sql/mall_b_precheck.sql`（information_schema 动态拼 SQL，兼容列/表不存在）、`mall_b_migration.sql`（A 阶段守卫、幂等加列、`@legacy_overtime` 回填、`create_time IS NULL` 落异常表、补 PENDING 消息）；`mall.sql` 同步 B 结构并为 65 条无列名位置 INSERT 补 NULL；`QueueEnum`/`RabbitMqConfig` 移除 A 的 TTL 延迟队列，改主队列 + DLQ + 固定 TTL 重试队列。索引 `idx_order_expire_scan` 用 `(status, delete_status, id, expire_time)`，避免 `Using filesort`。
